# C无需重训的修复与验证方案（2026-10-11）

今天只完成CPU审计与设计，**未修改任何核心控制代码**，未启动GPU、SAPIEN或新评测。以下行为修改均待确认，以独立runner/配置实施；B/C checkpoint、统计和历史结果不可覆盖。没有承诺修复后的成功率。

## 优先1：明确状态边界，并增加接触后跟踪保护

- **证据**：#489对应代码已核实；C 410019/410021最佳对齐时左TCP目标—实测差约5.48/4.44cm，410009保持末端左差6.61cm。旧B完整qpos方案改善跟踪但3种子总体成功数与drive相同，说明反馈不是充分条件。
- **位置**：`BC_blind_runner.py::execute`与在线state构造；`BC_blind_telemetry.py::snapshot/real_gripper`；RoboTwin `robot.py::get_*_arm_jointState/get_*_arm_real_jointState/get_normal_real_gripper_val`。
- **原因**：驱动目标可在物理接触时继续推进；relative预测参考也跟着目标变化，图像却显示实际位置。夹爪“real”函数名误导。
- **修改设计**：新增明确`drive_command/drive_target/measured_qpos/measured_finger_m`字段，不改policy drive-state。在控制器侧根据实测arm跟踪误差限制下一条目标的推进速率/速度或暂停推进，逐步验证阈值；如改从实测qpos插值，保留policy的drive输入并明确这样可能改变下一轮状态分布，单独作为新方案，不同时改horizon。先增加只记录不干预的版本。不可把上一目标直接宣称真实状态，不可直接修改旧checkpoint统计。
- **对C影响**：权重不变；仅记录时模型输入及轨迹不变；任何目标投影/限速属于新“模型+控制器”实验，必须与原drive_h5分开报告。
- **CPU验证**：现有纯mock测试已证实执行器算式与动作前缀；下一步用mock制造target≠qpos，验证阈值、关节限位、两臂同tick和无NaN；历史日志重放只能验证触发率，不能预测物理反事实。
- **GPU验证**：独立开发种子原方案vs仅新增保护，每动作60ms不变，记录原始预测和投影后的目标、真实跟踪、官方首次成功与保持，不能替专家动作。
- **影响/不确定性**：可能减少接触后命令越走越远；可能拖慢抬升、陷入死锁或放大夹持力，需保留回退。毫米级跟踪仍失败的例子不会因此自动解决。

## 优先2：双臂相对位姿与保持阶段约束

- **证据**：5条曾双侧对齐但未有效抬升；410012末端左距离4.382cm而跟踪仅4.06mm；410009翻转。410006双侧接触持续但短时违反官方条件，不能只用contact=True判抓稳。
- **位置**：`BC_blind_runner.py::execute/rollout`，`BC_blind_telemetry.py::snapshot`及`recovery_fk.py::poses`；RoboTwin `lift_pot.py::check_success`只读取不改。
- **原因**：单臂逐关节目标可被正确执行，但两臂相对间距/抬升方向/高度协同不正确；闭环模型在接触分布外可能继续拉扯物体。
- **修改设计**：先从qpos→FK添加相对TCP平移、姿态及双侧高度差指标。保存首次双侧接触的参考但不将它当完美抓握；随后小规模测试联合速度/相对运动限制与更短h2（分两次单因素实验）。保持相位启用条件须用可实际获得的测量，不按种子切换。若使用仿真真实锅pose/官方抓取点作约束，明确这是有特权状态的诊断控制器，不能与纯RGB+关节模型基线混标。不能通过执行专家抬升或冻结动画冒充模型成功。
- **对C影响**：仅加记录不影响；动作投影、horizon或相位门控会改变控制配置，权重不变。h2仍执行2×60ms，不把动作周期缩成别的时间。
- **CPU验证**：已存arm qpos可做独立FK/相对平移曲线；新增纯NumPy几何约束mock应测试左右对称、边界连续、零增量、关节限位。日志只可证明已发生的几何问题，不能证明约束必能抬起。
- **GPU验证**：先独立开发种子，比较定位/双侧接触/高度/倾角/滑落；保持2秒继续真实模型重规划。额外保存目标投影量和夹爪实际米值。
- **影响/不确定性**：可能改善相对拉扯与保持，但错误接触姿态被锁定反而可能使抬升失败。旧B drive_h1已有0/3，不能声称缩块必有改善；C要独立验证。

## 优先3：修正评测口径与失效事件记录（最确定、最安全）

- **证据**：#482的expert_check默认门控在本地源码确认；昨日base0只按model_id筛选。保持统计501tick多计已由CPU复算证实，9/20及6/20不变；旧日志失效tick仅bool，完整状态60ms可能错过阈值变化。
- **位置**：`BC_blind_runner.py`的hold窗口及`execute`事件记录，`BC_blind_background.py`汇总；`select_C_blind_base0_seeds.py`筛选与新版本实验manifest；官方`eval_policy_xpolicylab.py`作为对照，不直接修改。
- **原因**：起始状态样本不能作为一个时间区间；专家可行条件改变分母分布；低频状态快照不能精确确定首个失效条件。
- **修改设计**：统计窗口改为`first < tick <= first+500`，保存独立修正CSV，不覆盖原指标。每首成功、首失效、接触建立/失去、严重跟踪误差tick保存完整状态和判定分项；保存pose全四元数/相对TCP、qvel、实际指米值和碰撞分类。评测manifest显式expert_check=false/base0/fixed60ms。以后增加expert-conditioned独立协议，专家只做模型评测前可行性筛选，并冻结新的候选/通过seed清单，绝不进入模型动作执行。
- **对C影响**：记录及指标修正不影响模型/旧成功次数；expert筛选改变评测样本分布，不能声称模型本身提升，更不能替换昨天45%结果。
- **CPU验证**：已复算9条保持窗口，去起始tick后501→500窗口，官方保持统计均一致；可在mock中构造0.004s瞬时违规，验证记录精确时刻、每分项原因及事件只触发一次。专家可行性无法靠CPU历史数据确认。
- **GPU验证**：恢复GPU后仅新开发诊断中验证事件记录；正式expert筛选需独立仿真，获得授权再运行。新测试必须采用未调参seed并固定控制。
- **影响/不确定性**：本项本身不提高真实成功率，但能消除虚假的时长提升和不可比基准，准确判断下一项改动是否有效。
